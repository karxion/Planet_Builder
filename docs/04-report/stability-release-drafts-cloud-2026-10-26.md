# 배포 통합·아이템 초안 복구·클라우드 충돌 방지

작업일: 2026-10-26. 사용자 지정 순서대로 배포 통합 → 초안 복구 → 클라우드 충돌 방지를 구현했다. 클라우드 프로젝트는 아직 없으므로 사용자가 승인한 범위는 코드·테스트·설정 문서이며, 실제 서버 활성화는 포함하지 않는다.

## 1. 배포 통합

- GitHub main에 포함된 40자리 커밋에서 Git archive로 앱 전체를 추출한다. Sites 체크아웃은 호스팅 운반용으로만 사용한다.
- 대상 Git 루트·깨끗한 작업 트리·Site ID·경로/symlink를 확인하고, env·개인 지도·분석 출력·의존성 런타임은 소스로 복사하지 않는다.
- 테스트 설정과 ignore 규칙도 고정 커밋에서 가져온다. 이전 공개판의 별도 코드·의존성 버전과 추적된 테스트 캐시를 제거했다.
- `.openai/release.json`에 GitHub 커밋·정규화된 소스 해시를 기록하고 빌드에서 재검사한다. 정보 탭과 `/build-info.json`에 앱 버전·커밋·스키마 버전을 제공한다.
- 텍스트의 CRLF/LF만 정규화한 해시와 vendor 원본 바이트의 SRI 검증을 함께 사용한다. 단순히 두 저장소의 Git 커밋 문자열이 같아야 한다는 뜻은 아니다.
- 실제 공개용 소스 기준 커밋: `68d4b6adf6832c3e3c1657f263687f46d1fea0e7`.
- 소스 해시: `a6c0ae86ec41428bb2be2451b88767d6f25ebf73eb4f5b0ae53b2f8ff48f173b`.
- 게시 도구의 인증·업로드는 여전히 명시적으로 수행한다. GitHub Actions 자동 게시 연동까지 새로 구성한 것은 아니다.

절차: `docs/02-design/single-source-release.md`.

## 2. 아이템 초안 복구

- 별도 메모리 Map을 제거하고 공통 `EditorDrafts`에 `item:<id>` 원시 폼 값을 저장한다.
- 기존 자동 보존(750ms 유휴, 지속 입력 시 최대 3초), 프로젝트 전환 경고, 로컬 복구 기록과 초안 상태 표시를 재사용한다.
- 이름·메모뿐 아니라 유형·희귀도·유니크 여부·소유주·던전 보상·레퍼런스 선택도 포함한다. 검색어는 초안에서 제외한다.
- 복구 경계는 현재 프로젝트에 존재하는 아이템만 허용하며 필드·enum·크기·프로젝트 ID/스냅샷 ID를 검증한다.
- 복원된 값은 적용 전 초안이다. FPB·클라우드·데이터 출력에 자동으로 섞지 않으며 적용/폐기를 명시적으로 구분한다. 이미지는 기존처럼 별도 적용되는 필드다.

### 실제 화면 테스트에서 추가 수정한 기존 버그

레거시 `.map` 로더는 완료 후 `showStatistics()`를 호출했다. 이 함수가 통계 표시 외에 새 mapId와 `map:generated` 이벤트를 발생시켜, FPB 복구 도중 프로젝트 세션을 다시 초기화했다. 단위 테스트의 mock 로더에는 이 부작용이 없어 기존 검사만으로 발견되지 않았다.

- 가져온 지도는 `showStatistics(false)`로 저장된 mapId를 유지하고 새 지도 생성 이벤트를 발생시키지 않는다.
- 최초 지도 준비 대기는 생성·불러오기 이벤트 모두 처리하되 한 번만 실행한다.
- 클리핑된 좌표 격자가 D3의 null path를 반환할 때 `round(null)`로 오류가 나던 경로도 빈 경로로 처리한다.
- 원시 레거시 함수 실행 테스트로 불러오기/신규 생성의 이벤트 차이를 검증했다.

### 직접 확인한 결과

1. 새 아이템의 이름과 GM 메모를 수정하고 적용 버튼을 누르지 않았다.
2. 복구 기록에서 `적용 전 초안 1개`, `초안 로컬 보존 최신`을 확인했다.
3. 페이지를 새로고침했다.
4. `자동 저장 복구됨`과 초안 1개를 확인했고, 원래 저장된 이름의 목록에서 해당 아이템을 선택하자 수정 중이던 이름·GM 메모가 그대로 표시됐다.
5. 초안 폐기를 누르면 저장된 원래 이름으로 돌아갔다.

## 3. 클라우드 충돌 방지

- 가변 `projects` 레코드의 GET 후 PATCH를 제거했다. `project_revisions`에 저장·이름 변경·삭제 리비전을 추가하는 append-only 프로토콜이다.
- 논리 프로젝트 UUID와 숫자 revision을 유지한다. 서버의 **UNIQUE(createdBy, revisionKey)** 제약이 동일 사용자의 동일 r+1 저장을 하나만 허용한다. 서버 409를 충돌로 표시한다. 사전 조회는 빠른 안내일 뿐 최종 동시성 방어가 아니다.
- 클라이언트 UPDATE/DELETE를 금지하는 owner-only RLS가 필수다. 삭제는 새 tombstone을 추가하며 과거 리비전에서 프로젝트가 되살아나지 않게 최신 숫자 revision으로 목록을 만든다.
- 새 파일 업로드 뒤 리비전을 추가한다. 경쟁에서 진 저장의 새 파일만 정리하며, 커밋 여부가 불명확한 네트워크/5xx/408 오류에서는 삭제하지 않는다. 이전 파일은 참조가 남아 있으므로 즉시 삭제하지 않는다.
- `VITE_BKEND_CONCURRENCY=immutable-v1`은 실제 인덱스·RLS 검증 후에만 설정한다. 미설정 시 업로드·이름 변경·삭제를 요청 전에 차단한다. 기존 로컬 FPB 기능은 그대로 사용한다.
- 공식 문서의 publishable API key 헤더·필터·페이지네이션과 중복 생성 409를 참고했다. 실제 서비스의 인증/파일 API까지 연결 검증한 것은 아니다.

독립 클라이언트 테스트: 동시 저장 정확히 하나 성공, 이름 변경 대 삭제의 단일 승자, tombstone 뒤 과거 값 부활 방지, 성공 응답 유실 후 파일 보존, 서버 제약 미설정 시 네트워크 쓰기 0회. 이는 UNIQUE를 구현한 모의 서버 검사이며 실제 bkend 테스트가 아니다.

설정/활성화 전 실계정 체크리스트: `docs/02-design/bkend-cloud-setup.md`.

### 남은 운영 작업

- bkend dev/staging/prod 생성, 테이블·소유자 권한·복합 고유 인덱스·private 파일 설정.
- 두 실제 계정의 접근 차단과 두 PC 동시 저장 검증 후 클라우드 활성화.
- 과거 리비전·파일은 보존된다. 용량 회수용 서버 GC와 영구 삭제/보존 기간 정책은 후속 작업이다.
- 기존 가변 `projects` 데이터는 자동 삭제/변환하지 않는다. 실제 데이터가 있다면 백업 후 관리자 마이그레이션이 필요하다.

## 검증과 한계

- 작업본: 91개 테스트 파일, 996개 통과. 타입 검사 통과.
- 통합 배포 소스도 91개 파일·996개 전체 테스트, 타입 검사, Vite 빌드를 통과했다. 이전 529/138개 별도 공개 테스트 경로에 의존하지 않는다.
- 실제 브라우저에서 초안 작성·자동 보존·새로고침 복구·폐기·정보 탭 출처 표시를 확인했다.
- 추가로 기존 FPB 파일 열기를 시도했으나 브라우저 파일 입력의 CDP 응답이 중단돼 완료 여부를 확인하지 못했다. 해당 파일 호환성 테스트를 통과했다고 보고하지 않는다.
- 전체 Playwright E2E는 저장소 방침에 따라 자동 실행하지 않았다. 모바일 실기기·실제 클라우드 인증/권한은 미검증이다.
