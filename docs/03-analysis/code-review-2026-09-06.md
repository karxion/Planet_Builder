# 판타지 행성 빌더 실행·UI·구현 점검

- 점검일: 2026-09-06
- 대상: `codex/fantasy-planet-builder`의 현재 작업 트리
- FMG 기준선: `03a10502b0293b2afdb37b506f8b25178ce06c4f`, v1.135.0
- 방법: bkit code-review 기준의 코드 검토, 실제 브라우저 조작·스크린샷 확인, 빌드·단위 검사, 격리된 재현 검사
- 변경 범위: 이 보고서와 재현 스크립트만 추가. 제품 코드는 수정하지 않음.

## 결론

기본 지도 생성, 기존 FMG 편집기 접근, 3D 구체 표시, 프로젝트 압축 기반은 동작한다. 그러나 **저장 신뢰성, 2D/3D 좌표 일치, 설정 적용, 시드 재현성**에 출시 전 수정할 문제가 있다. 현재 상태를 기획서의 v1 완료로 판단하기는 어렵다.

기존 `fantasy-planet-builder.analysis.md`의 Pass 판정 중 3D 위치 동기화, 캔버스 하단 일치, 로컬 복구는 이번 시나리오에서 반례가 나왔다. 기존 검사는 "캔버스가 나타나는가 / 2D로 전환되는가"를 확인했지만, "같은 장소인가 / 모든 변경이 복구되는가"까지 보장하지 않는다.

아래 증거는 구분해서 읽어야 한다.

- **실화면 재현**: 실행 앱에서 조작하고 스크린샷 또는 DOM 상태로 확인.
- **격리 재현**: 현재 소스와 실제 지도 fixture 또는 mock HTTP로 확인. 실제 bkend 서버 검증이 아님.
- **코드 확인**: 구현 경로에서 확인한 결함 또는 위험. 별도 실서비스 재현은 하지 않음.

## 주요 발견

### F01. P1: 레이어 변경이 자동 저장에서 누락됨

**증거: 실화면 재현 + 코드 확인**

1. 자동 저장 복구 후 기존 Layers 메뉴를 연다.
2. `States`를 눌러 국가 색상 레이어를 끈다.
3. 화면에서는 국가 색상이 사라졌지만 상단은 계속 `자동 저장됨`이다.
4. 10초 이상 지난 후 새로고침하면 국가 색상이 다시 나타난다.

DOM의 `#statesBody path`도 변경 직후 0개, 복구 후 34개로 확인했다. 이미 저장된 것처럼 표시된 작업이 복구되지 않는 문제다.

**위치:** `src/services/planet/planet-builder.ts:127`, `:128`, `:313`; `src/services/io/load.ts:337`

현재 변경 감지는 document의 `change`와 초기 `#map`의 `pointerup`에 의존한다. 레이어 버튼의 click은 빠지고, 지도 불러오기는 SVG를 교체하므로 초기 SVG에 연결한 이벤트도 사라진다. 카메라 조작 역시 저장 이벤트와 연결되지 않는다.

**수정 방향:** 편집·레이어·카메라 변경을 명시적인 프로젝트 변경 이벤트로 모으고 revision 기반 dirty 상태를 둔다. 저장 시작 시점의 revision과 완료 시점을 비교해 저장 중 추가 편집을 `저장됨`으로 잘못 표시하지 않는다.

**완료 기준:** 레이어, 도시 이름, 지형 브러시, 카메라를 각각 바꾼 뒤 유휴 저장·새로고침으로 복구 검증. `.map`/`.fpb` 불러오기 이후에도 동일 검사.

### F02. P1: 설정 변경·저장·생성 취소가 일관되지 않음

**증거: 실화면 재현 + 코드 확인**

- 이름을 `QA 이름 변경 테스트`로 입력하고 설정을 닫은 뒤 상단 저장을 누르면 `기기에 저장됨`으로 표시된다. 새로고침 후 설정 이름은 이전 `새로운 판타지 행성`으로 돌아왔다. 다운로드 파일 자체를 다시 열어 확인한 것은 아니지만, 파일 생성 코드도 폼 대신 이전 `settings`를 직렬화한다.
- 생성 확인창이 나타나는 상태에서 이름을 `QA 취소한 이름`으로 변경하고 생성 후 `Cancel`을 누르면 지도 경로는 동일한데 설정 이름은 변경된 채 남고 상태는 `행성 생성 중`이다.

**위치:** `src/services/planet/planet-builder.ts:172`, `:192`, `:241`, `:259`; `public/modules/ui/options.js:725`

폼은 생성할 때만 수집하고, 수집한 값은 생성 확인 전에 내부 상태와 localStorage에 반영한다. "설정 적용"과 "세계를 새로 생성"의 경계가 없다.

**수정 방향:** 이름·표시 설정과 재생성이 필요한 생성 설정을 분리한다. 입력 초안과 확정 설정을 분리하고, 확인 및 생성 성공 후 확정한다. 취소·실패 시 기존 지도·설정·저장 상태를 유지한다.

**완료 기준:** 이름만 바꿀 때 지도가 재생성되지 않음. 취소 시 모든 상태 불변. 파일 저장·자동 저장·복구에서 같은 이름 보존.

### F03. P1: 3D에서 선택한 장소가 2D의 반대 경도로 이동함

**증거: 실화면 재현 + 코드 확인**

1440×900, 시드 `260906`으로 생성한 행성에서 Jing/Famhdran/Yoshish 쪽 서쪽 대륙을 정면에 두고 중심을 더블클릭했다. 2D는 Longan/Yeunglia/Khonia 쪽 동쪽 대륙으로 확대되었다. 단순 모드 전환 성공이 아니라 실제 장소 불일치다.

**위치:** `src/renderers/view-3d-renderer.ts:934`, 특히 `:945`; 텍스처 배치 `:986`

전체 지도 텍스처를 좌우 반전 없이 그리는데 선택 좌표는 `(1 - uv.x) * graphWidth`로 뒤집는다. 지역 지도에서는 텍스처의 오프셋·패딩도 역변환하지 않는다.

**수정 방향:** 지도 좌표→텍스처 UV→구면 좌표 및 역변환을 하나의 투영 어댑터로 통일한다. 지역 지도 바깥의 바다 패딩 클릭은 원본 셀 선택으로 처리하지 않는다.

**완료 기준:** 적도·양극 근처·동서 각 사분면의 알려진 위치 및 지역 `.map`에서 왕복 좌표 오차를 검증한다. 화면 테스트는 선택 전후 지명 또는 셀 ID까지 비교한다.

### F04. P1: 손상된 FPB가 검증을 통과하고 현재 설정을 오염시킬 수 있음

**증거: 격리 재현 + 코드 확인**

`climate`, `view`, `source`가 없고 `mapPayload`가 단순 101글자인 JSON도 `decodePlanetProject`가 정상 반환한다. 음수 반지름도 통과한다. 이후 `loadProject`는 설정을 먼저 바꾸고 localStorage에 기록한 뒤 `updateForm`에서 `settings.climate`를 접근하므로 실패할 수 있다.

**위치:** `src/services/planet/project-codec.ts:79`; `src/services/planet/planet-builder.ts:290`

**수정 방향:** 스키마 전체, 유한한 수치·범위, enum, 카메라, 배열, FMG 페이로드를 경계에서 검증한다. 압축 전후 크기에 상한을 둔다. 기존 프로젝트 백업 및 새 프로젝트 검증·로드 완료 후 상태를 교체한다. 실패 시 이벤트 리스너·타임아웃도 정리한다.

**완료 기준:** 누락 필드, 잘린 gzip, 잘못된 JSON, 지원하지 않는 버전, 과대 파일을 열어도 현재 지도·이름·자동 저장본이 유지된다.

### F05. P1: 같은 시드·행성 설정이 화면 크기에 따라 다른 세계를 만듦

**증거: 실화면 재현 + 코드 확인**

시드 `260906`과 같은 폼 설정으로 1440×900에서는 1440×720 지도를, 1920×1080에서는 1920×960 지도를 생성했다. 지형과 국가 구성이 달라졌다. 두 경우 실제 FMG 시드 입력도 `260906`이었다.

**위치:** `src/services/planet/planet-builder.ts:203`, `:118`; `src/types/planet-project.ts:11`

생성 좌표계를 `window.innerWidth`로 결정하지만 이를 `PlanetSettings`에 저장하지 않는다. 무작위 생성 후 실제 시드를 `settings.seed`에 되돌려 기록하는 경로도 없다. 기존 FMG의 다른 생성 옵션·lock 상태도 행성 설정만으로 완전히 재구성되지 않는다.

참고로 같은 화면 크기에서 재생성한 국가 SVG 경로도 34개/33개로 달랐다. 이는 추가 결정성 조사 신호이며, 모든 숨은 옵션을 격리한 데이터 배열 비교는 아니므로 별도 원인으로 확정하지 않았다.

**수정 방향:** 논리적 지도 크기·셀 해상도를 화면과 독립시키고, 생성에 사용한 실제 시드와 모든 유효 생성 옵션을 프로젝트에 저장한다. RNG 초기화와 grid 재사용 경로를 점검한다.

**완료 기준:** 서로 다른 화면 크기와 깨끗한 세션에서 높이·문화·국가 데이터 해시가 동일해야 한다. 저장된 지도 재열기와 시드 재생성은 별도 테스트한다.

### F06. P1: 클라우드 revision 검사가 동시 저장을 막지 못함

**증거: 격리 재현 + 코드 확인. 실제 bkend 서버 미검증**

현재 코드를 mock HTTP에서 실행해 같은 revision 1을 가진 두 클라이언트가 동시에 저장하도록 했다. 둘 다 성공했고 최종 revision은 2, 파일은 마지막 클라이언트의 `file-2`가 되었다. 두 업로드 사이에 손실된 버전에 대한 충돌 오류가 없다.

**위치:** `src/services/planet/bkend-repository.ts:106`, `:140`

사전 GET 비교 후 파일 업로드와 무조건 PATCH가 분리되어 있다. 클라이언트 비교만으로는 원자적 충돌 방지가 되지 않는다.

**수정 방향:** 서버에서 expected revision을 조건으로 갱신하는 원자적 작업을 제공하고 조건 불일치 시 충돌 응답을 반환한다. 검증된 API 계약 없이 임의로 헤더만 추가해서 해결됐다고 판단하지 않는다. 메타데이터 갱신 실패 시 새 파일 정리·재시도 규칙도 필요하다.

**완료 기준:** 실제 두 세션 동시 저장에서 하나는 성공, 다른 하나는 충돌 처리. 보존 선택 시 서로 다른 프로젝트로 유지. 두 계정의 RLS·private 다운로드 접근 차단도 별도로 검증.

### F07. P2: 행성 설정 중 일부는 효과가 없거나 명칭과 다른 동작

**증거: 코드 확인**

- 반지름, 하루 길이, 자전축 기울기는 폼·타입·저장에만 있고 렌더러나 거리 계산에 전달되지 않는다.
- 해수면은 지형 높이 또는 실제 해양 비율에 적용되지 않는다. 15 이하이면 초대륙, 25 이상이면 군도로 프리셋을 바꾸며, 16~24는 동일한 선택 프리셋을 사용한다.
- 선택한 대륙 형태가 해수면 값에 의해 조용히 무시될 수 있다.

**위치:** `src/services/planet/planet-builder.ts:176`, `:220`; `src/renderers/view-3d-renderer.ts:914`

**수정 방향:** 자전축→구체 자세, 자전 주기→표현 속도, 반지름→거리 단위 변환을 연결한다. 해수면과 목표 해양 비율의 의미를 확정하고 실제 생성에 반영한다. 지원 전에는 효과가 있는 조절기처럼 노출하지 않는다.

### F08. P2: 3D 캔버스가 전체 작업 영역을 채우지 못함

**증거: 실화면 재현 + 코드 확인**

1440×900에서 새 행성 생성 직후 3D 전환 시 캔버스 상단은 58px, 높이는 662px, 하단은 720px였다. 화면 아래 180px에 2D 지도가 그대로 보였다. 구체 자체는 정상적으로 렌더링되므로 "비어 있지 않은 캔버스" 검사만으로는 통과한다.

**위치:** `src/controllers/view-3d.ts:80`; `public/planet-builder.css:20`

논리 지도 높이와 화면 높이를 혼용하고 WebGL setSize의 inline 크기가 CSS보다 우선할 수 있다.

**수정 방향:** 공통 작업 영역의 실제 bounding box로 renderer 크기·카메라 aspect를 계산하고 ResizeObserver로 갱신한다. 지도 생성 해상도와 표시 해상도를 분리한다.

**완료 기준:** 1440×900·1920×1080, 생성 직후·복구 직후·리사이즈 후 모두 캔버스 하단=작업 영역 하단. 의도하지 않은 2D 노출 없음.

### F09. P2: 두 개의 보기·저장 체계로 화면과 프로젝트 상태가 불일치

**증거: 실화면 재현 + 코드 확인**

기존 Layers 메뉴의 `Globe`를 누르면 구체가 표시되지만 새 상단의 `2D 지도`가 활성 상태로 남았다. 영어 3D 설정창도 별도로 뜬다. 기존 Save/Load와 새 저장/열기가 함께 보여 어떤 형식·상태를 저장하는지 구분하기 어렵다.

**위치:** `src/services/planet/planet-builder.ts:131`, `:253`, `:307`; `src/controllers/view-3d.ts:68`

새 셸의 `viewMode`와 기존 controller 상태가 분리되어 있다. 로드도 globe 분기만 명시적으로 복원한다. 실제 구체를 보고 있어도 2D로 직렬화하거나 카메라를 빠뜨릴 수 있다.

**수정 방향:** 보기 상태를 controller 한 곳에서 소유하고 모든 진입점이 이를 사용하게 한다. 파일 메뉴에 FPB 프로젝트 저장, 지도 내보내기, 기존 MAP 가져오기를 구분해 통합한다. 불러오기 시 map/globe 양쪽 모두 명시적으로 복원한다.

### F10. P2: 기존 지도 가져오기 호환성과 구면 배치가 계획과 다름

**증거: 격리 재현 + 코드 확인. 지역 지도의 실제 UI 가져오기는 미검증**

- 실제 `demo.map` fixture를 LF 줄바꿈으로 바꾸면 래핑을 거부한다. CRLF 검사를 강제하는 반면 상위 파싱은 LF도 허용한다.
- 파일 선택은 `.gz`를 허용하지만 FPB 외 파일은 `file.text()`로 읽어 압축된 MAP을 해제하지 않는다.
- 지역 지도 텍스처는 계획한 중앙 배치·바다 패딩 대신 기존 구름 텍스처와 `dx = mapWidth / 4` 경로를 사용한다.

**위치:** `src/services/planet/project-codec.ts:22`, `:44`; `src/services/planet/planet-builder.ts:276`; `src/renderers/view-3d-renderer.ts:976`

**수정 방향:** 확장자뿐 아니라 gzip magic을 보고 해제한다. 지원 FMG 버전·줄바꿈 정책을 정의하고 가져오기 어댑터를 통일한다. 원본 좌표를 보존하는 명시적 패딩 변환을 프로젝트에 저장한다.

### F11. P2: 클라우드 이름 변경이 다음 저장에서 되돌아감

**증거: 격리 재현 + 코드 확인. 실제 bkend 서버 미검증**

목록 이름을 `Renamed`로 변경한 후 기존 로컬 프로젝트를 저장하면 이름이 `Client B`로 돌아가는 것을 재현했다. rename은 메타데이터만 바꾸며 FPB 내부 이름과 현재 프로젝트 상태를 갱신하지 않는다.

**위치:** `src/services/planet/bkend-repository.ts:158`; `src/services/planet/planet-builder.ts:475`

**수정 방향:** 이름의 기준을 하나로 정하고 rename을 revision이 있는 프로젝트 변경으로 다룬다. 현재 열린 프로젝트라면 메모리·폼도 갱신하고, 다시 열어도 같은 이름이어야 한다.

추가 결정 필요: 클라우드 프로젝트를 연 상태에서 `행성 생성`은 현재 프로젝트 덮어쓰기인가, 새 프로젝트 생성인가? 지금은 `currentCloudProject`가 유지된다. 별도 `새 프로젝트` 동작과 명확한 저장 대상을 제공해야 한다.

### F12. P2: PWA 시작 경로가 하위 경로 배포와 맞지 않음

**증거: 코드 확인. 설치·오프라인 실기기 검증은 미수행**

`vite.config.ts:5`는 Netlify 외 환경에서 `/Fantasy-Planet-Builder/`를 base로 사용하지만 `public/manifest.webmanifest:9`는 `/?source=pwa`로 시작한다. 하위 경로 설치에서는 앱 대신 사이트 루트로 이동할 수 있다. Netlify 루트 배포에는 이 특정 경로 문제가 해당하지 않는다.

**수정 방향:** manifest start_url·scope·서비스 워커 범위를 배포 base와 일치시킨다. 캐시 설치 성공과 실제 오프라인 재시작·lazy-loaded 3D 사용을 production build로 검증한다.

## UI 직관성 평가

직접 확인한 1440×900, 1920×1080, 390×844 화면 기준이다. 모바일은 v1 편집 범위 밖이므로 보조 관찰로 분리한다.

| 항목 | 관찰한 문제 | 개선 제안 |
|---|---|---|
| 편집 기능 발견 | 지형·국가·도시·레이어 편집이 작은 화살표 뒤 영어 메뉴에 숨어 있음 | 항상 보이는 레이어/편집 진입점과 한국어 명칭 제공 |
| 시각적 일관성 | 흰색 한국어 상단과 분홍색 반투명 영문 FMG 패널이 별개 제품처럼 보임. 작은 글씨와 배경 지도 때문에 스캔이 어려움 | 패널의 배경·글꼴·행 높이·선택 상태를 통일. 기존 편집기를 기능 단위로 점진 통합 |
| 현재 프로젝트 식별 | 상단은 앱 이름만 표시하며 작업 중인 행성 이름과 저장 대상이 보이지 않음 | 행성 이름, 로컬/클라우드 대상, 마지막 저장 시각을 작업 공간에 표시 |
| 설정과 생성 | 이름 변경에도 유일한 적용 동작이 `행성 생성`임 | 프로젝트 속성 저장과 지형 재생성을 분리 |
| 출력 발견 | 지도 PNG/SVG는 기존 Export, 행성 캡처는 설정 패널에 분산 | 하나의 내보내기 메뉴에서 지도 PNG/SVG·행성 PNG 선택 |
| 3D 제어 | 새 셸은 기존 3D 설정창을 닫아 회전·조명·텍스처 제어 진입점이 불명확함 | 구체 보기 전용의 작은 도구 모음. 자동 회전 토글·조명·레이어 선택 |
| 작업 상태 | 레이어 변경 후 `자동 저장됨`, 생성 취소 후 `생성 중` 등 실제 상태와 모순 | 저장 대상별 상태와 오류 후 복구 동작을 상태 머신으로 관리 |
| 언어 | 생성 확인창, Layers/Tools, 기존 편집 기능은 영어 | 공통 번역 사전과 영어 폴백. 생성 지명 언어와 UI 언어는 별도 설정 |
| 작은 화면 | 390px에서 클라우드 모달과 하단 보기 전환은 표시되지만 설정 버튼은 숨김 | 모바일은 조회용 범위를 명확히 정의하고 기본 프로젝트 정보 접근 유지 |

우선 통합할 화면 구조는 **상단 프로젝트·파일 동작 / 좌측 레이어·편집 도구 / 중앙 지도·구체 / 우측 선택 항목 속성**이다. 장식보다 지도 영역과 반복 작업의 접근성을 우선한다. 전체 프레임워크 교체는 필요하지 않다.

접근성 추가 점검: 닫힌 설정 패널은 transform과 aria-hidden만 적용되어 있으므로 키보드 초점 제외 처리가 필요하다. 보기 버튼에는 선택 상태의 접근성 속성, 저장 알림에는 적절한 live region을 추가하는 것이 좋다. 키보드 전체 탐색은 이번 검사에서 완료하지 않았다.
